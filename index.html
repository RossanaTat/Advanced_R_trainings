Intro on OOP and S3 methods

  • OOP: based on objects, which have a class, - what the object is -, and a method - what the object does
  • classes are organized into hierarchies so that if a method is missing for a certain class, it is inherited from the parent
  • Main goal of OOP: polymorphism, so that you can consider the function interface separately from the function implementation
  • S3 methods are most commonly used OOP system in CRAN packages, they are an implementation of functional OOP:
    • methods belong to generic functions
    • method calls look like ordinary functions calls

The basics

  • An S3 object is a base type with at least a class attribute(e.g., factor)

  • It behaves differently from its underlying base type whenever it’s passed to a generic function, which:

    • uses a different implementation (the method) depending on the class of an argument

    • finds that method by performing method dispatch

You can use sloop::s3_dispatch() to see the process of method dispatch:

library(sloop)
f <- factor(c("a", "b", "c"))
s3_dispatch(print(f))
=> print.factor
 * print.default

Classes

  • no formal definition of a class, to make an object an instance of a class, you simply set the class attribute
# Create and assign class in one step
x <- structure(list(), class = "my_class")

# Create, then set class
x <- list()
class(x) <- "my_class"
  • You can determine the class of an S3 object with class(x), and see if an object is an instance of a class using inherits(x, "classname").
class(x)
[1] "my_class"
inherits(x, "my_class")
[1] TRUE
inherits(x, "your_class")
[1] FALSE

Class name guidelines:

  • Any string can be a class name, but it’s advised to keep it simple by using only letters and underscores (_). Avoid using periods (.) in the class name because it could be confused with the period separator used between a generic name and a class name in R (e.g., generic.class).

  • When using classes within a package, it’s a good idea to include the package name in the class name (e.g., mypackage_myclass). This reduces the risk of class name collisions

Three recommended functions for class management:

1. Constructor: new_myclass()

  • Purpose: The constructor is a low-level function that is responsible for creating new objects of your class with the correct internal structure.

2. Validator: validate_myclass()

  • Purpose: The validator is used to check if the object’s internal values are valid or meet certain conditions.

  • What it does: It performs more computationally expensive checks to ensure that the object’s fields contain correct data

3. Helper: myclass()

  • Purpose: The helper function is a convenience function for users to easily create objects of your class. It is typically a wrapper around the constructor function.

Example

# Constructor
new_my_factor <- function(values, levels) {
  stopifnot(is.character(values), 
            is.character(levels))
  structure(
    list(values = values, 
         levels = levels),
    class = "my_factor"
  )
}

# Validator
validate_my_factor <- function(x) {
  if (!all(x$values %in% x$levels)) {
    stop("All values must be in levels.")
  }
  x
}

# Helper function
as_my_factor <- function(x, levels = unique(x)) {
  x <- as.character(x)
  validate_my_factor(new_my_factor(x, levels))
}

# Example usage
f <- as_my_factor(c("low", "medium", "high"), levels = c("low", "medium", "high"))
print(f)

Generics and methods - method dispatch

  • every generic calls UseMethod to perform method dispatch. UseMethod() takes two arguments: the name of the generic function (required), and the argument to use for method dispatch (optional)
  • it creates a vector of method names, paste0("generic", ".", c(class(x), "default")), and then looks for each potential method in turn..see this in action with sloop::s3_dispatch()
  • “default” class is not a real class, but is included to define a standard fallback that is found whenever a class-specific method is not available.

Most generics are very simple, and consist of only a call to UseMethod(), for example see

Creating methods

  • Best Practice: Only create methods for generics or classes that you own (or collaborate with the author of the package/class to add your method).
  • Argument Matching: Your method should have the same argument signature as the generic, except when using … for flexibility.
  • Ellipsis (…): Using … in methods allows you to accept additional arguments, but be careful because misspelled arguments will be silently ignored, which could cause hidden issues.

Inheritance

Mechanism through which different classes can share behavior, powered by 3 ideas:

1. Class can be a character vector

2. If method not found for the first class, R looks to method for the second class

3. A method can delegate work by calling NextMethod(), “->”

   [.default
-> [ (internal)

Output takeaways

Step 1: Printing

- The print() function is called on the result of ordered(“x”)[1].

- R first tries print.factor, which is the specialized print method for factors (including ordered factors).

- The => symbol means this method was used.

- The * before print.default means it was skipped, because print.factor was found.

–> Since an ordered factor is also a factor, R uses print.factor to display it

Step 2: Subsetting

- When ordered("x")[1] is evaluated, R looks for a [.ordered method (a special method for subsetting ordered factors).

- No => appears next to [.ordered, meaning it was not found.

- R then falls back to [.factor, which exists and is used (=> means this method was applied)

- -> [ (internal) means that the base “‘\[’” operator was used at the lowest level

–> Ordered factors don’t have a specialized [.ordered method, so they rely on [.factor.

–> The actual subsetting operation is ultimately handled by the internal [ function.

Why delegation to -> [ (internal)

In R’s S3 method dispatch system:

  • R first looks for [.ordered, but it doesn’t exist.
  • It then finds [.factor and uses it (=> means it was applied).
  • Inside [.factor, R calls NextMethod(), which means:
    • It delegates the call to [.default (if it exists) or the base [ function.
    • Since [.default is not used here, it goes directly to [ (internal).

–> 💡 Key takeaway:

-> [ (internal) means that [.factor did not completely handle the operation itself but instead delegated the actual work to the base R `[ function (written in C). This delegation is likely happening via NextMethod()

Relationship between the classes that appear together in a class vector

In our example, ordered is a subclass of factor and factoris a superclass of ordered.

It is recommend that you adhere to two principles when creating a subclass:

  1. Sub-class and class belong to the same base type
  2. Attributes of the subclass should be a superset of the attributes of the superclass.

Example

# Function to create a "labelled_factor" subclass
labelled_factor <- function(x, label) {
  # Ensure the base type remains the same as the superclass (factor)
  if (!inherits(x, "factor")) {
    stop("x must be a factor")
  }
  
  # Add an extra attribute ("label") while preserving existing attributes
  structure(x, class = c("labelled_factor", "factor"), label = label)
}

# Example usage
x  <- factor(c("low", "medium", "high"))
lf <- labelled_factor(x, label = "Risk Level")

# Check structure
str(lf)
 Factor w/ 3 levels "high","low","medium": 2 3 1
 - attr(*, "label")= chr "Risk Level"

NextMethod()

Let’s start with an example

new_secret <- function(x = double()) {
  stopifnot(is.double(x))
  structure(x, class = "secret")

print.secret <- function(x, ...) {

  invisible(x)

`[.secret` <- function(x, i) {

With NextMethod() instead

`[.secret` <- function(x, i) {
  new_secret(NextMethod())
}
x[1]
[1] "xx"
s3_dispatch(x[1])
=> [.secret
   [.default
-> [ (internal)

  • NextMethod() tracks the list of potential next methods: this means that R keeps track of the method dispatch chain, which consists of all the possible methods that could be invoked next for the object being processed

  • When a method is called, R checks the class of the object and finds the corresponding method. If the method defines a call to NextMethod(), R will continue searching for the next method in the chain, considering the inheritance hierarchy and class structure

Allowing sub-classes

Subclassing might allows for more flexible and extensible code. To allow subclasses, the parent constructor needs to have...and class arguments:

new_secret <- function(x, ..., class = character()) {
  stopifnot(is.double(x))

  structure(
    x,
    ...,
    class = c(class, "secret")
  )
}
#note that the class argument is used to attach the class to the object, and "secret" is added to the class chain.
  • Subclasses (like supersecret) can be created by simply calling the parent constructor with the class argument modified to the subclass name.
new_supersecret <- function(x) {
  new_secret(x, class = "supersecret")
}

To allow inheritance, you need to think about your methods, as you can no longer use the constructor. See the example below:

x2 <- new_supersecret(c(15, 1, 456))

More on UseMethod, NextMethod, and default method in S3

UseMethod():

  • the mechanism that triggers method dispatch in S3 -dispatch appropriate function based on the class of the object passed to it
  • It’s used in the generic function

Consider this example, what rules of function evaluation does UseMethod() violate?

g <- function(x) {
  x <- 10
  y <- 10
  UseMethod("g")
}

g.default <- function(x) c(x = x, y = y)

x <- 1
y <- 1

g(x)
 x  y 
 1 10 
g.default(x)
x y 
1 1

Comments

  • x remains 1 because arguments are passed unchanged to methods.
  • However, local variables in g() (excluding function arguments) are accessible inside the method: y is taken from the local environment of g(), where it was set to 10, not from the global environment.
  • When UseMethod() dispatches a method, it preserves the environment where the generic function was called.
    • Arguments (x) are explicitly passed, so they cannot be modified by the generic
    • Other variables (y) inside the generic function are still available in the method’s evaluation environment

2 takeaways: 1. Arguments are normally evaluated in the function’s environment, but UseMethod() ignores changes inside the generic 2. Normally, local variables in a function are not visible in called functions, but UseMethod() makes them available —

NextMethod():

  • used inside a method to call the next method in the dispatch chain
  • If a method is called for a subclass, the NextMethod() function is used to call the corresponding method of the superclass, keeping the method dispatch chain intact

default methods:

  • Fallback methods that are used when no more specific method is found for a particular class
  • useful when you want to provide a generic implementation of a function for all object types, while still allowing specific classes to override the method with specialized behavior
  • necessary if you want to ensure that a function works for any object, even if that object doesn’t have a specific method defined for it
  • unnecessary when you want to ensure specific behavior for each subclass or class in a way that does not fall back on a generic implementation

Example:

# Define generic class
area <- function(x) {
  UseMethod("area", x)
}

# Define the specific methods
# Circle area
area.circle <- function(x) {
  pi * x$radius^2
}
# Square area
area.square <- function(x) {
  x$side^2
}
# Rectangle area
area.rectangle <- function(x) {
  x$length * x$width
}

# Define the Default Method
area.default <- function(x) {
  stop("No method for calculating area for this class.")
}
# Create some objects and call the function

# Create a circle
circle <- list(radius = 5)
class(circle) <- "circle"

# Create a square
square <- list(side = 4)
class(square) <- "square"

# Create a rectangle
rectangle <- list(length = 6, width = 3)
class(rectangle) <- "rectangle"

# Create a generic object (no specific class)
unknown_shape <- list()
class(unknown_shape) <- "unknown"

# ________ ####

Area of square: 16

3. EASIER WAYS OF CREATING NEW VECTORS CLASSES

For example, in R you might need to define methods for a lot of different generics. {vctrs}, instead, gives some documentation/support: e.g., which methods you need to define depending on what you want the vectors to do.

Basics: create a new vector class by calling new_vctr() , this creates an object of class vctrs_vct which has a number of methods

Percent class

Let’s make a make a percent class, i.e., a double vector that is printed as a percentage. Start by defining a low-level constructor to check types and/or sizes and call new_vctr(). percent is built on a double vector of any length and doesn’t have any attributes.

new_percent <- function(x = double()) {
  if (!is_double(x)) {
    abort("`x` must be a double vector.")
  }
  new_vctr(x, class = "vctrs_percent")
}

x <- new_percent(c(seq(0, 1, length.out = 4), NA))

percent <- function(x = double()) {
  x <- vec_cast(x, double())

is_percent <- function(x) {

as_percent.character <- function(x) {
  value <- as.numeric(gsub(" *% *$", "", x)) / 100
  new_percent(value)

2. Creating an S3 Generic Function with UseMethod()

let’s create a generic function that will “reveal” the numbers hidden by the “x” representation.

# Define a generic function for revealing secrets
reveal <- function(x) {

reveal.secret <- function(x) {

}

}

3. Inheritance and NextMethod()

When we define a subclass like supersecret, it inherits all properties and behaviors of its parent class secret. However, it can also introduce additional attributes or behaviors.

Why use NextMethod()? * It ensures that the superclass method is properly called. * It allows supersecret to inherit behavior from secret.

new_supersecret <- function(x = double(), level = "high") {
  stopifnot(is.double(x))
  structure(x, class = c("supersecret", "secret"), level = level)
}

y <- new_supersecret(c(99, 1000))

attributes(y)
$class
[1] "supersecret" "secret"     

$level
[1] "high"

How method dispatch work in this case

Let’s define a method for printing supersecret objects:

print.supersecret <- function(x, ...) {
  cat("Super Secret! Hidden level:", attr(x, "level"), "\n")
  NextMethod()  # Calls the parent print method (print.secret)
}

y <- new_supersecret(c(99, 1000), level = "top")
print(y)

[1] "supersecret" "secret"

Then, NextMethod() ensures that print.secret() still runs.

Additional methods

Let’s define an S3 generic function that behaves differently based on the class.
Example: Masking Numbers More for supersecret objects

mask_number <- function(x) {
  UseMethod("mask_number")
}

mask_number.secret <- function(x) {
  strrep("x", nchar(x))
}

mask_number.supersecret <- function(x) {
  strrep("*", nchar(x))  # Stronger masking for supersecret
}

mask_number(s)   # "xx"  "x"   "xxx"
Error: object 's' not found
mask_number(ss)  # "**"  "*"   "***"
Error: object 'ss' not found

If an object doesn’t match any specific method, R falls back to default methods.

mask_number.default <- function(x) {
  stop("mask_number() is not implemented for this object type.")
}
mask_number("hello")
Error in mask_number.default("hello"): mask_number() is not implemented for this object type.
# Error: mask_number() is not implemented for this object type.

This prevents unexpected errors for unsupported types.

4. Subsetting and Keeping the Subclass

When we define a subclass (supersecret) of secret, it inherits all methods of secret. However, if we subset the object, the subclass information gets lost.

Let’s consider the current situation:

x <- new_supersecret(c(15, 1, 456))
class(x)
[1] "supersecret" "secret"     
x_subset <- x[1:2]
class(x_subset)
[1] "secret"

Why does this happen? * By default, the subsetting operator ([) from base R drops attributes
* The class vector is an attribute, so unless we manually reapply it, subsetting a supersecret object returns just a secret object

Using vctrs::vec_restore()

Instead of manually setting the class, we can use:

`[.secret` <- function(x, ...) {
  out <- NextMethod()  # Perform subsetting
  vctrs::vec_restore(out, x)  # Restore subclass information
}

It automatically restores all attributes

x_subset <- x[1:2]
class(x_subset)
[1] "supersecret" "secret"     
attributes(x_subset)
$level
[1] "high"

$class
[1] "supersecret" "secret"
